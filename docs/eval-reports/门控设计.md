# 门控设计：从关键词表到向量质心（面试口径）

> 一句话版本：**VL 图片向量只对"视觉描述型"查询有价值，对"任务意图型"查询是噪声（朴素三路融合 Recall@1 -0.167 的负结果）。门控决定谁走 VL：v1 是关键词表，v2 升级为向量质心相似度判定——阈值用种子留一法自动校准，查询向量复用文本召回已算好的结果，零额外调用；英文/新词探针泛化 8/14 → 14/14；向量不可用时自动回退 v1 规则。**

## 1. 为什么要有门控（先讲负结果，再讲方案）

同一评测集（24 素材 × 45 查询，真实模型）：

| 策略 | Recall@1 | Recall@5 | MRR |
|---|---|---|---|
| B 文本向量 RRF（两路） | 0.733 | 0.911 | 0.828 |
| D 朴素三路融合（VL 全量开） | **0.567** | 0.778 | 0.697 |
| E2 门控三路（只给视觉查询开 VL） | 0.733 | **0.956** | 0.851 |

- D 比 B 差：VL 文本-图片对齐噪声把语义查询的前几名全部灌成图片（"下雨天适合听什么"返回 5 张图）；
- 门控后不但恢复还反超（Recall@5 0.911 → 0.956）：视觉查询从 VL 获益，语义查询不再被污染。
- 结论：**多模态信号应该按查询意图启用，而不是无脑融合**——这是整个门控的存在理由。

## 2. v1 → v2 演进

| | v1 关键词规则 | v2 向量质心（当前默认） |
|---|---|---|
| 判定 | 命中 27 个视觉词表（色/夜空/剪影…）即视觉 | 查询向量与"视觉描述/任务意图"两个质心比距离 |
| 阈值 | 无（命中即真） | 留一法（LOO）自动校准 +0.0044 |
| 新词/英文 | 失效（词表覆盖不到） | 可分（bge-m3 多语言同空间） |
| 成本 | 零 | 零（复用查询向量）+ 种子嵌入每进程 1 次 |
| 角色 | **降级为兜底**（向量不可用时） + 消融基线（`gate_kw`） | 默认（`gate`） |

实现：`backend/app/retrieval/gate.py`，检索接入在 `search.py` 的 `use_vl` 分支。

## 3. 面试三连问的标准答案

**Q1：种子表哪来的？会不会又是拍脑袋？**
- 种子是 40 条**意图描述性示例**（视觉描述 20 条 + 任务意图 20 条，中英各半），不是关键词枚举——描述的是"这类查询长什么样"，不是"出现哪些词就算"；
- 刻意与评测查询集**不相交**，避免用测试集校准（测试集泄漏是评测的另一个拷打点，主动交代）；
- 上线后的维护路径：从检索日志里挖门控误判的查询说法，补进对应种子组即可，判定逻辑零改动。

**Q2：阈值是多少？怎么定的？**
- 校准出来的 **+0.0044**（margin = sim_visual − sim_semantic，≥ 阈值判视觉），方法是对 40 条种子做**留一法**：每条种子用"它不在场"的质心算 margin，在 LOO margin 上取平衡准确率最高的阈值——不是手工拍定；
- 泛化间隔可以背下来：库外探针上**视觉类最小 margin +0.086，语义类最大 margin -0.149**，两类完全分开，阈值落在间隔正中间，说明边界不贴着任何一类。

**Q3：换语言、新词怎么办？**
- bge-m3 本身是多语言模型，中英文在同一向量空间，门控天然跨语言；
- 用 **14 条库外探针**（中文新词 5 条如"霓虹灯牌在雨夜的街头闪烁"、英文视觉 3 条、中英任务意图 6 条，与种子集零重叠）实测：**v1 关键词规则 8/14（57%），v2 向量质心 14/14**；
- v1 的 6 个误判全是新词和英文——这正是升级的动机，报告里有逐条误判明细。

## 4. 成本与延迟（面试官必问"代价"）

- **查询侧零额外调用**：文本向量召回本来就要嵌入查询，门控直接复用同一个向量，纯本地矩阵运算；
- **种子嵌入每进程一次**：40 条短文本一次批量请求，构建后常驻内存；构建失败 5 分钟后允许重试，期间走关键词兜底；
- **降级链**：无 Key / API 超时 → 自动回退 v1 关键词规则，检索永不阻塞。这也回答了"为什么还留着关键词表"。

## 5. 端到端指标怎么看？——评测暴露的下一课（最硬的部分）

51 条查询（45 中文 + 6 条英文查中文库的跨语言查询）上的实测：

- **中文查询**：E1/E2 端到端一致——评测集内的视觉查询都含显式视觉词，v1 词表覆盖得住；
- **跨语言查询暴露了一个真问题**：v2 门控把英文视觉查询**判型全对**（如 "city skyline at night"，margin +0.175，v1 关键词表对英文完全瞎），但 E2 的 Recall@1 反而比 E1 低 0.059——因为 **VL 的跨语言"英文文本→图片"对齐弱于 bge-m3 的"英文文本→中文描述"对齐**，判对意图后启用 VL，反而让 VL 通道把别的图片顶到首位（Recall@3/@5 不受影响）；
- 这给出门控 v3 的演进方向：**按收益门控（gate-on-benefit），而不是按意图门控**——"这是不是视觉查询"和"VL 对这条查询有没有增益"是两个问题，v2 回答的是前者，线上用点击反馈/ interleaving 学后者；
- 生产默认是 full 策略（融合 + 重排精排），重排把 R@1 兜到全场最高（0.814），所以这个 gap 在线上被吸收——但评测把它暴露出来，这正是"评测驱动"的价值：**指标会告诉你下一个该做什么**。

面试讲法：先讲 v2 的泛化收益（探针 57% → 100%），再主动讲跨语言反噬的发现和 v3 方向——"我知道我的方案在哪类输入上会输，也知道下一步拿什么数据修它"，这比"指标全涨"可信得多。

## 6. 主动交代的局限与下一步（防深挖）

1. **质心是线性边界**：意图分布复杂后可升级为轻量意图分类器（查询向量上接逻辑回归/小 MLP，标注数据从线上日志挖）——这正是题库给的第二个演进方向，当前数据规模下质心够用；
2. **CLIP 零样本判别**是另一条路，但要引入重依赖，与现有 bge-m3 栈不兼容，当前收益不成比例；
3. **`full` 策略仍全量开 VL**（重排兜底消化了噪声），后续可让 full 也走门控，省 VL 嵌入调用的钱；
4. **种子风格偏"描述句"**，对超短查询（"蓝"单词）的判定分布需要线上日志验证；
5. 顺带（题库点 4）：**RRF 融合前已剔除 BM25 零分文档**（`search.py` 中 `if v > 0`），否则每个素材都会拿到 1/61 的 RRF 保底分污染排序——这个细节代码里一直有，讲的时候别漏。
