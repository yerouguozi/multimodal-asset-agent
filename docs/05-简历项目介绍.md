# 简历项目介绍（可直接使用）

## 一句话定位

**多模态素材管理 Agent**：不预设领域的素材中心，上传什么素材就自动长出什么领域；统一入库流水线 + 跨模态语义检索 + LangGraph 素材助理，全栈实现并自带评测。

## 简历项目经历（推荐写法）

**领域自适应多模态素材管理 Agent**（个人项目 | Python / FastAPI / LangGraph / React）

- 构建图片/视频/音频/文档四模态统一入库流水线：异步任务队列、SHA-256+pHash 去重、缩略图生成、视觉理解（描述/标签/OCR）、语音转写、文档摘要、统一向量化，失败自动重试、成本可追踪；
- 自实现 BM25（jieba 中文分词 + 字符二元组）+ bge-m3 向量双路召回，RRF 融合 + bge-reranker 重排，字段权重随素材分布自适应；自建 24 素材/45 查询评测集（含语义改写与纯视觉查询）量化对比五种检索策略：文本向量 RRF 把 Recall@1 从 0.611 提到 0.733；实测发现朴素多模态融合反而劣化（-0.167），实现"按查询类型门控启用图片级 VL 向量"后 Recall@5 达 0.956、MRR 0.851；重排精排最终 Recall@1 0.789 / MRR 0.893 零失败；
- 用 LangGraph 编排素材助理 Agent（意图识别 → 工具调用 → 组织回答，SSE 逐步推送），支持语义检索、素材详情、领域画像、文生图入库、素材压缩/转格式；
- 领域画像由数据驱动：标签聚合 + LLM 洞察自动生成"素材库属于什么领域"，无需预设分类；
- Agent 升级：LLM 结构化任务规划 + LangGraph 多步循环执行（"压缩 #3 再生成封面"）、会话记忆落库、SSE 逐步推送；
- 进阶检索：音视频分片转写 + 时间戳检索（"找我说过 XX 的那一段"，ffmpeg 切块 + SenseVoice）、以图搜图（VL 图片向量）、Milvus 可选向量后端（与本地 npz 实测结果一致）；
- 工程化：模型路由（小图走 8B 大图走 32B）+ 每次调用成本追踪、JWT 认证、Docker Compose 部署、GitHub Actions CI、63 个 pytest 用例（LLM/网络全 mock）；
- 自研工具链闭环：接入自有 agent-qc-platform 对本 Agent 做质量评测（CustomerServiceDriver 协议，4/4 用例通过）。

## 面试高频问题与回答要点

1. **"这和你调 API 有什么区别？"**
   模型只是零件：跨模态统一语义空间（全部模态归一为描述文本嵌入）、检索策略（BM25+向量 RRF+重排）是自己设计并用评测集验证的；流水线、路由、降级、成本控制都是工程活。

2. **"检索指标怎么来的？"**
   自建 24 素材/45 查询评测集（含语义改写、纯视觉查询与库外反例），逐策略跑 Recall@k/MRR/NDCG。三条实证结论：BM25 只覆盖表面词重叠；文本向量解决语义改写；**朴素多模态融合是负结果**（VL 图片向量把语义查询前几名灌满图片，Recall@1 -0.167），改成按查询类型门控启用后 Recall@5 达 0.956，重排兜底后 Recall@1 0.789 / MRR 0.893 零失败。

3. **"模型路由怎么做的？"**
   按图片边长路由：≤640px 走 Qwen3-VL-8B，大图走 32B；每次调用记 UsageLog，前端显示估算成本。

4. **"Agent 怎么保证不胡说？"**
   工具结果是事实来源、LLM 只是发言人（沿用数据平台项目的一贯原则）：工具全确定性、返回结构化结果，LLM 只能基于结果组织语言；空结果如实说明；写操作（生成/处理）需要用户明确指令。

5. **"遇到过的坑？"**
   - 推理模型（deepseek-v4-pro）把输出预算花在思维链上导致 content 为空 → 加大 max_tokens + 从 reasoning_content 兜底提取；
   - np.savez 会对非 .npz 路径自动补后缀导致向量静默不落盘 → 被自建评测集暴露并修复；
   - asyncio.Queue 跨线程投递不安全 → run_coroutine_threadsafe 桥接到主事件循环。

6. **"为什么用 SQLite/本地向量库？"**
   MVP 用 SQLite + 本地 npz 向量库，存储层全部走抽象接口，可平滑换 PostgreSQL/Milvus；优先把业务闭环跑通，再谈基础设施。
